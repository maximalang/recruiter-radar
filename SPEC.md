# Recruiter Radar — product specification

**Версия:** 5.0  
**Обновлено:** 2026-07-15  
**Статус:** действующий продуктовый контракт

## 1. Назначение

Recruiter Radar — Russia-first, evidence-first радар клиентских возможностей для рекрутинговых агентств. Он находит компании, которым стоит написать сейчас, объясняет причину, показывает доказательства и предлагает законный корпоративный путь контакта.

Продукт не является ATS, CRM, парсером ради объёма, системой поиска кандидатов или инструментом массовой рассылки.

Основной цикл:

`Landing → live preview → pilot → client profile → Telegram digest → feedback → suppression/reweighting → better digest`

## 2. Продуктовый контракт лида

Каждая рекомендация должна отвечать на вопросы:

1. Какая это компания и насколько надёжно установлена сущность?
2. Что изменилось и почему это важно сейчас?
3. Почему компания соответствует профилю агентства?
4. Какие независимые доказательства подтверждают сигнал?
5. Каков безопасный корпоративный путь контакта?
6. Какое следующее действие рекомендуется?
7. Какие негативные сигналы или ограничения снижают уверенность?

По умолчанию хранятся данные уровня компании. Персональные email и телефоны не собираются без отдельного требования и review. AI может готовить черновик сообщения, но не отправляет массовый outreach автоматически.

## 3. FIUR scoring

`Total = Fit + Intent + Urgency + Reachability`

Каждая компонента ограничена диапазоном `[0, 1]`, итог — `[0, 4]`. UI может показывать производное значение `1–100`, но доменный контракт остаётся FIUR `[0, 4]`.

- **Fit:** ICP, функция роли, индустрия, география, размер, исключения.
- **Intent:** релевантные вакансии, свежесть, hiring burst, независимое подтверждение, прямая карьерная страница.
- **Urgency:** burst, сложные роли, новый регион, корпоративное событие, повторные или зависшие вакансии.
- **Reachability:** сайт компании, career page, общий HR-контакт, безопасный неперсональный маршрут.

Каноническая реализация: `apps/web/lib/scoring/fiur.ts`. Подробное продуктовое объяснение: `docs/product.md`.

## 4. Confidence gates

| Gate | Критерий | Доставка |
|---|---|---|
| A | 2+ независимых слоя evidence, чистый entity match, прямой company surface | автоматическая доставка |
| B | один сильный источник плюс enrichment | доставка с меткой уверенности |
| C | только platform aggregation или сомнительный entity match | обязательный review |
| D | контекст без прямого подтверждения найма | не является лидом |

Высокий score не обходит confidence gate.

## 5. Источники и доказательства

Source registry описывает роль, качество, статус и базовую уверенность источника. Активность источника определяется реализацией и registry, а не roadmap-текстом. Текущее состояние проверяется командами:

```text
npm run source:list
npm run verify:sources:readiness
npm run verify:sources:coverage
```

Рекомендации должны быть evidence-backed, дедуплицированы на уровне организации и устойчивы к повторному ingest.

## 6. Доставка, feedback и entitlement

Telegram — основной канал digest. Callback должен быть аутентифицирован, идемпотентен, replay-safe, записан в audit trail и отражён в будущих suppression/reweighting решениях.

Premium delivery разрешена только после server-side проверки entitlement: активный pilot/subscription, лимиты профилей и лидов, разрешённый канал. Billing webhook хранится в event ledger и обрабатывается идемпотентно.

## 7. Архитектурные границы

- Next.js и PostgreSQL владеют продуктовым ядром.
- Production orchestration: VPS cron → `/api/cron/daily-radar`.
- n8n декомиссионен и не развёртывается в production.
- Scoring, entity resolution, confidence, billing, suppression, digest state и prompt versioning живут только в коде приложения.
- Внешний ввод валидируется; SQL параметризован; auth и tenant boundary проверяются server-side.
- Секреты, `.env*`, dumps, build output и локальные QA-артефакты не коммитятся.

## 8. Проверка изменений

Минимальный gate для кода:

```text
npm run web:check
```

`npm run web:build` запускается для runtime/build-sensitive изменений после успешного check. Миграции, billing, auth, scoring, confidence, dedupe, feedback и Telegram требуют усиленного review согласно `CLAUDE.md`.

Workflow разработки и git-порядок описаны в `docs/development-workflow.md` и `AGENTS.md`.

## 9. Иерархия документации

При конфликте применяются в порядке приоритета:

1. `AGENTS.md` и `CLAUDE.md` — обязательные правила выполнения и безопасности.
2. `SPEC.md` — текущий продуктовый контракт.
3. `docs/product.md` и `docs/architecture.md` — детальная модель продукта и архитектуры.
4. Датированные файлы в `docs/specs/` — исторические или task-scoped решения; они не переопределяют текущий контракт без явного статуса.
5. Отчёты, планы и research-документы — справочный материал, а не источник runtime-истины.
