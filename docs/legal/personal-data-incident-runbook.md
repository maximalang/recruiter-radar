# Runbook: инциденты персональных данных

Требования: 152-ФЗ ст. 21 ч. 2.2–2.3 — уведомление Роскомнадзора о факте
неправомерной передачи/доступа в течение **24 часов** с момента получения информации,
о результатах внутреннего расследования — в течение **72 часов** (см.
legal-research-2026-08.md §4). Публичная Политика уже фиксирует эти сроки.

Этот документ внутренний. Не публиковать детали архитектуры, секреты, схемы доступа.

## 1. Идентификация и эскалация

- Источники: алерты health/логов, сообщение пользователя, уведомление процессора,
  внешняя публикация об утечке.
- Любой член команды → владельцу продукта немедленно; владелец ведёт таймлайн
  (время обнаружения = T0).

## 2. Локализация и остановка

Действия по обстановке (не все нужны): ротация `SESSION_SECRET` и ключей провайдеров;
отзыв всех сессий (`auth_security_events: all_sessions_revoked`); временное отключение
затронутого канала доставки; блокировка скомпрометированных webhook'ов; снапшот
состояния для расследования.

## 3. Оценка факта

- Какие системы затронуты (по data-map.md).
- Категории данных (аккаунт/платежи/профиль/публичные данные компаний).
- Была ли неправомерная передача/доступ к ПДн (порог ст. 21 ч. 2.2).
- Масштаб: число субъектов/записей.

## 4. Сохранение доказательств

Логи, записи `auth_security_events`, `billing_webhook_events`, дампы на изолированном
носителе. Ничего не удалять до завершения расследования.

## 5. Уведомление регулятора

- Решение о применимости принимает владелец (при сомнении — консультация юриста,
  но не ценой пропуска 24 часов).
- Подача через портал РКН (pd.rkn.gov.ru); содержание: факт, время, масштаб,
  предварительные меры.
- Через ≤72 часов — результаты расследования: причины, меры, устранение.

## 6. Уведомление субъектов

Если риск для прав субъектов высок (например, утечка e-mail + хэшей сессий,
позволяющая фишинг): сообщение о факте и рекомендуемых действиях. Текст согласует
владелец; паникёрские формулировки и раскрытие уязвимости не допускаются.

## 7. Координация процессоров

Robokassa (если платёжный контур), Яндекс.Облако (почта), Timeweb (хостинг) — запрос
их логов/позиции в рамках их процедур.

## 8. Пост-мортем

Не позднее 5 рабочих дней после закрытия: причина, хронология, исправления
(патчи, ротации, изменения процессов), обновление этого runbook и retention-schedule.

## Записи

Каждый инцидент получает внутренний ID `PD-INC-YYYY-MM-DD-NN`; материалы хранятся
вне публичного репозитория минимум 3 года.
